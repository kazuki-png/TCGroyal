# TCG ROYAL 融資アプリ デザイン仕様案

作成日：2026年11月1日。対象：iOS・Androidの利用者アプリ、対応する融資管理画面。実装前のレビュー版。

利用者がカードを選び、複数枚をまとめて査定依頼し、正式な条件を確認して融資を受け、返済・返却まで追える構成にする。画面ごとに現在の状態、次の操作、金額の意味を明示する。

## 合意済みの方針

| 項目 | 方針 |
| --- | --- |
| 対象サービス | カード担保融資。直接買取は本家TCG ROYALで扱い、このアプリには追加しない |
| フッター | 左からホーム、取引状況、申し込み、お知らせ、マイページの5項目 |
| 中央タブ | 「申し込み」。丸いボタンで強調する。別名の「カード検索」はタブにしない |
| ブランド | 本家と同じロゴを左上に配置。黒背景・金色のアクセント・日本語のみ |
| 申込単位 | 複数カードを一つの案件にまとめる。現在の上限20種類・合計100枚を維持 |
| カードの入口 | 名前・型番検索、画像検索、見つからないカードの個別相談 |
| 本人確認 | 当面は運転免許証の表裏提出と運営確認。JPKIは今回の実装対象外 |
| 検索と価格 | 外部サービスとの連携はバックエンド内に置く。利用者向けの通常画面ではスニダン名・ロゴを表示せず、「カード検索」「融資参考額」に統一。登録済みカード・個別相談も維持する。契約等で必要な表示がある場合は対応する |
| 見積もり | カード選択時に自動計算。参考額は正式な提示額・借入残高と分ける |
| 管理 | アプリ・LINE・管理者作成案件を同じ取引履歴に統合。状態変更を通知する |
| 環境 | Previewは右上の小さな環境ラベルからテスト機能を開く。本番には表示しない |
| 今回の作業 | 調査・仕様化のみ。アプリ実装、APK更新、デプロイ、DB変更は行わない |

この文書のうち、上表以外の画面詳細は採用を推奨する仕様案。金利・本人確認の適法性・配送責任など運用判断が必要な項目は末尾にまとめる。競合の条件は自社の取引条件として転用しない。

### 2026年11月1日の実装状況

2026年11月3日のv1.18.0更新では、以下の履歴に加え、中央タブからのカメラ起動、撮影後の自動検索、手動検索の入力時検索、PSA10初期値のグレードドロップダウン、追加後のカード一覧と継続・申請への分岐を実装する。ここでの自動検索は撮影・写真選択後の1回の検索であり、ライブ映像の自動認識・自動撮影ではない。

v1.17.0では5タブと中央の丸い申し込み、ホーム、検索の入口統合、画像と候補の比較、明示的なグレード選択、複数枚リスト、暗号化したカード下書き、相談と契約の統合一覧、条件・返済・延長・履歴の画面分割、返済予定日の必要額参照、提供元を表示しない検索・参考額のUIを更新する。新しいDBマイグレーションは使用しない。

この時点では、ゲスト検索、検索入力時の自動検索、鑑定番号の個体別保存とQR、自由記述・希望額・確認工程まで含む下書き復元、配送追跡の登録、振込先の登録・表示、通知日時のカスタマイズ、免許証表裏の一括送信・具体的な不備理由、実際の退会処理、iOS標準ナビゲーションへの移行は未実装。カード検索はログイン後に明示的な検索操作で実行し、画像・個人情報・口座・パスワードをカード下書きに保存しない。これらは対応する運用条件・API・データ設計の確定を含む後続作業とする。

返済額参照は、対象契約の所有権確認後に、既存DBの精算用関数を用いる読み取り専用処理。予定日末、満期日は契約期限時点を基準とし、実際の入金照合額とは区別する。銀行への振込・入出金台帳・金利の変更は行わない。

## 情報構成とナビゲーション

| タブ | 目的 | ルート画面 | 下層画面 |
| --- | --- | --- | --- |
| ホーム | 現在の状況と必要な手続きを確認 | 利用状況サマリー | 優先取引の詳細、本人確認、申込下書き |
| 取引状況 | 相談・申込・契約を探す | 対応が必要／進行中／完了 | 取引詳細、条件確認、発送、返済、延長、返却、相談 |
| 申し込み | カードを選び査定を依頼 | カードを追加 | 検索結果、画像読取、候補確認、カード詳細、申込リスト、申込内容確認 |

中央の丸ボタンは「申し込み」。押すとカメラのプレビューを開く。初回はカメラ権限を要求し、拒否時も手動検索・写真選択へ進める。タブの再タップでも撮影の入口へ戻り、追加済みカードは保持する。撮影や外部AIへの送信はタブを押しただけでは実行しない。円の直径56、タップ領域64以上、下に「申し込み」を表示。左右は各2項目。申込リストの枚数は円付近の小さな数値バッジで表示し、アクセシビリティ名にも含める。

通常のタブ内画面とカード撮影の入口ではフッターを表示する。OSの写真選択・書類撮影ではシステムの戻る・閉じる操作を使う。画面遷移時は本文を先頭へ戻し、主要操作が以前のスクロール位置に隠れないようにする。

### 戻る動作

- タブごとに独立した履歴とスクロール位置を保持する。異なるタブへの移動は戻る履歴に積まない。
- Androidのシステム戻る・端からの右スワイプは、モーダルを閉じる、編集中の子画面を戻る、詳細から一覧へ戻る、の順に一段だけ処理する。
- 各タブのルートではAndroid標準の終了・バックグラウンド動作に任せる。ログアウトや下書き削除はしない。
- iOSは下層画面で標準の戻るスワイプを使い、タブルートでは終了動作を割り当てない。
- お知らせから開いた取引は戻ると元のお知らせへ戻る。通知からのコールド起動では、お知らせから開いた取引詳細という復帰先を構成する。
- 下書きは自動保存。未保存の個人情報編集を離れる場合は「編集を破棄／編集を続ける」を表示する。
- 通信中に戻っても確定操作を取り消したことにはしない。結果不明時は受付照会を行う。不可逆な処理中だけ離脱を一時抑止し、タイムアウト後は照会・復帰を可能にする。
- 非表示タブの戻るハンドラー、通知イベント、遅延した通信結果で、今見ている画面を勝手に移動させない。

## ホーム

初回は「カードを選んで申し込む」を主ボタンにし、検索・写真の入口、3段階の利用手順、利用条件、よくある質問を置く。広告的なコピー、ランキング、ニュースの大きなカルーセルは置かない。

ログイン後は次の順序にする。

1. 対応が必要な手続き。期限が近いもの・条件承諾・追加情報提出などを最大3件表示。
2. 借入元本の合計、最も近い返済期限、対象契約。「全契約を見る」で取引一覧へ。
3. 進行中の取引を最大3件。受付番号、代表画像、合計枚数、現在地、次の操作を表示。
4. 保存した申込下書き。「続ける」と「削除」。新規申込で上書きしない。
5. 最新のお知らせを最大2件。サポートへの入口。

複数契約では各期限を混ぜた一つの返済予定にしない。「最も近い期限」は契約番号と対象金額を併記する。古いキャッシュには更新時刻を表示し、最新確認までは金額確定・承諾ボタンを有効にしない。

## 申し込みとカード検索

### 基本フロー

中央の申し込み → カメラ → 撮影して検索、または手動で検索 → 候補を確認 → 拡大画像・カード情報・グレード・枚数 → 参考額を自動計算 → 申込に追加 → 追加完了メッセージと現在の申込カード一覧 → 続けてカードを登録する／登録を終了して申請に進む → 登録情報・書類等を確認 → 申込内容確認 → 査定依頼を送信 → 受付番号と次の操作を表示。現行APIではこの入口の利用にログインが必要。

参考額を見るためだけに本人確認書類を求めない。正式な査定依頼はログイン必須。ゲストでの検索・参考額・下書き作成を推奨するが、現行APIは認証が必要なため、匿名向け読み取り専用APIと利用制限の追加が前提。ゲスト利用を提供できない期間は、申し込みタブでログインを案内して検索可能と誤表示しない。

### 検索画面

- カメラの「手動で検索」から上段の「カード名・型番で検索」欄へ進む。検索画面には「撮影して探す」を置く。
- 現在の対応ゲームはポケモン・ワンピース。初期画面では両方を検索し、ゲーム種別はサーバー側で検証する。
- 日本語、英数字、全角半角、型番の空白等を正規化する。別カードを意味する記号・版情報を勝手に消さない。
- 入力中の検索は750ミリ秒の遅延、古い通信は中断・破棄。入力を消すと結果も消す。IME変換中の入力でも一定時間停止すると暫定検索するため、確定前の不要リクエストの抑制は改善余地がある。
- 名前一致だけで版を決めない。完全な型番一致、シリーズ・言語等を合わせた候補を優先する。
- 検索結果は標準2列グリッド。カード画像、正式名、型番、収録弾、言語を表示。大きい文字設定では1列リストに切り替える。
- 一覧で異なる状態の金額を一つの値にまとめない。参考額は詳細でグレード等を選んだ後に表示する。
- 登録DBと外部検索の同一カード候補を正規IDで統合し、重複表示しない。提供元のIDは内部に保持する。
- 外部取得失敗時も登録カード検索・個別相談は使える。検索元切替を利用者の復旧作業にしない。
- 0件では検索語修正、写真、見つからないカードを相談、の入口を表示。

### 画像検索

撮影画面に「撮影して検索」「手動で検索」「画像をアップロード」を置く。送信先・目的と本人確認書類の送信禁止を操作前に説明し、「撮影して検索」または「画像をアップロード」で送信に同意して実行する。撮影・選択後は追加の検索ボタンなしで読み取りと候補表示へ進む。画像と候補を表示し、名前・型番・版を利用者が照合する。自動で申込リストに追加しない。

撮影ガイドはカード全体を枠内に入れる、反射を避ける、型番が読める距離にする、を短く示す。カメラ許可は申し込みから撮影画面を開いた時に要求する。同じ表示中は拒否後に自動で要求を繰り返さない。拒否時は写真選択・手動検索を案内する。別タブ・バックグラウンドではカメラを停止する。リアルタイムの自動認識・自動撮影は初期実装に含めない。

初期は1回につきカード1枚の読み取り。読み取った候補を追加して連続撮影できる。1写真から複数カードを認識する方式は、切り出しと候補の紐付け精度を検証してから追加する。競合の「9枚」をそのまま自社上限にしない。

画像は既存の外部AI送信方針を引き継ぎ、送信先・目的・保持方針を送信前に説明する。競合の「外部AIへ送らない」という説明は転用しない。本人確認書類はこの経路に送らない。検索画像を実物の証拠写真として黙って再利用しない。

### カード詳細と追加

| 項目 | 入力・表示仕様 |
| --- | --- |
| 商品同定 | 画像、正式名、型番、収録弾、レアリティ、言語。曖昧な項目は確認が必要と表示 |
| 鑑定状態 | ドロップダウンの初期値はPSA10。PSA9以下、その他鑑定、未鑑定へ変更できる。初期値がPSA10であることと実物に合わせた変更を案内し、AI判定とは扱わない |
| 鑑定番号 | 任意。QR読取または手入力は入力補助。PSA APIでの自動照合は要求しない。未照合は自己申告と表示 |
| 枚数 | 1以上。減算・加算と数値入力。20種類・100枚の合計制限を加算前に検証 |
| 状態 | 傷・白かけ・折れ・ケース破損等を任意選択。状態を変えると参考額を失効させ再計算 |
| 参考額 | 読込中、算出済み、個別査定、期限切れ、取得失敗のいずれかを表示 |
| 操作 | 「申込に追加」。追加後の先頭に「xxxを申請に追加しました。」と現在の申込カード一覧。「続けてカードを登録する」で撮影へ戻り、「登録を終了して申請に進む」で申込内容確認へ進む |

鑑定番号がある個体は同一カード・同一グレードでも個体別に扱い、同じ番号の重複追加は警告する。番号なしの同条件カードは枚数としてまとめる。現行のCollateralItemには鑑定番号・写真等の個体情報がないため、実装時のデータ拡張が必要。

## 参考額と金額の表示

| 用語 | 意味 | 表示場所 |
| --- | --- | --- |
| 融資参考額 | 検索結果・申告状態・利用可能なデータから算出した目安 | カード詳細、申込リスト |
| 申込希望額 | 利用者が希望する金額 | 申込内容確認、申込履歴 |
| 正式な融資提示額 | 運営の現物確認後に提示する金額 | 条件確認 |
| 借入元本 | 実際に出金された元本 | ホーム、契約詳細 |
| 返済必要額 | 指定の基準日に必要な元金・利息等の合計 | 返済画面・契約詳細 |

価格データの提供元の相場価格・取引履歴をそのまま利用者に並べない。LTVや流動性スコアは初期画面に置かず、「参考額について」の説明に必要な範囲を記載する。提供元データ利用の許諾は公開前の確認事項。

### 外部サービスの表示とバックエンド連携

利用者向けのタブ、検索ボタン、見積もり、読み込み表示、通常エラーには提供元の商品名・ロゴを使用しない。「スニダン検索」は「カードを探す」、「スニダン価格から算出」は「融資参考額」に置き換える。提供元を選ぶ操作や、利用者による提供元アカウントへのログインは設けない。

外部サービスへのアクセスと認証情報はバックエンドで管理する。アプリには必要なカード情報、参考額、計算日時、有効期限、算出不可の理由だけを返し、外部APIのURL・認証情報・生のエラー・取引履歴を返さない。管理者向けには、利用権限のある担当者が提供元・取得日時・計算根拠を追跡できるようにする。

これは画面の簡素化とサーバーでの連携管理を目的とする。データを自社独自収集と偽る説明、必要な出典表示の削除、提供元のアクセス制限・検知を回避する仕組みは採用しない。契約上の出典表記や審査時の説明が必要な場合は、適切な表示箇所・資料に反映する。

カード選択・グレード・枚数変更後に自動計算する。短時間の連続変更はまとめ、前の応答が遅れても新しい条件の結果を上書きしない。画面を開いたまま無限再取得・無限再試行はしない。

現行の自動計算対象は条件付きのPSA10等に限られる。未鑑定を選べば必ず計算できるとは表示しない。相場不足・型番不一致・流動性不足・取得制限・未対応は、対応する理由を短く示し「個別査定で申し込む」へ進める。算出できない場合を0円や融資不可にしない。

全カードが計算できた時だけ参考合計を表示する。一部が未算出なら「算出済みの参考額 ¥X＋個別査定N種類」と表示し、合計・借入可能額とは呼ばない。参考額の一部があることを理由に、全カードの自動査定に同意させない。

更新時刻と有効期限を表示し、期限切れは金額をグレーにして「再計算」。正式条件の金額へ自動反映せず、再提示時は再承諾を必要とする。最低申込額・最大額・丸め単位はサーバー設定に従い、画面に有効な条件を表示する。現行実装は最低10万円、上限1,000万円、希望額1万円単位があるため、運営確認後に確定する。

## 申込リストと送信

リスト上部に種類数・合計枚数。各行に画像、名前、型番、状態、グレード、枚数、参考額と編集・削除を置く。下部に参考額の内訳と「申込内容を確認」。カードを削除しても取引履歴や過去の契約は消さない。

確認画面はカード一覧、希望額、本人確認の状態、登録住所、振込先、連絡方法、備考、申込時の同意を順に表示する。項目ごとに「変更」を置き、戻っても入力を失わない。書類提出は一連の導線で行い、既に確認済みなら繰り返し求めない。

査定依頼の同意と、後日の正式な融資契約の同意を分ける。申込ボタンは「査定依頼を送信」。送信後は受付番号、枚数、受付日時、次の手続き、取引を確認するボタンを表示する。「融資が完了しました」とは表示しない。

未鑑定・同定できないカードも個別相談として同じリストに入れられる。混在する場合は全体を運営確認へ回し、一つの受付番号を発行する。LINEは任意の相談窓口であり、LINEを開いたことを申込完了としない。

同一送信の連打・タイムアウト後の再送では同じ受付を返す。受付成功後に一覧取得だけ失敗した場合は「受付済み。取引状況を更新してください」と表示し、新規受付を作らない。受付状態が不明なら照会してから再送可否を決める。

## 取引状況と詳細

一覧の分類は「対応が必要」「進行中」「完了」。下書きは別の小さな領域に置き、受付済み案件の件数に含めない。相談・申込・融資を一つの一覧で確認でき、状態と受付日で絞れる。

一覧カードは受付番号、代表画像と残り枚数、代表カード名、合計枚数、状態、次の操作、最終更新を表示。まだ出金していない案件には借入残高を表示しない。管理者作成でアカウント未連携の案件は利用者一覧に出さず、本人確認済みの連携後に表示する。

詳細の順序は、状態と次の操作、重要な金額と期限、進捗、カード一覧、取引条件、配送・振込情報、手続き履歴、サポート。運営内部の保管場所や内部メモを利用者へ公開しない。

相談案件から契約が作られたら、一つの取引詳細内で「事前相談」と「融資契約」を時系列に表示する。既存の参照番号・ID・履歴を保持し、別契約の金額や配送を混ぜない。

## 正式条件と契約同意

正式提示額、月利と適用条件、期間・起算日、返済期限、費用、計算例、期限延長、質流れ、返却条件を確認できる画面にする。金利だけを小さく隠したり、参考額だけを大きく表示したりしない。

対象カードを全件確認でき、希望額から変わった項目には変更理由を表示する。利用規約等の文書版、条件版、有効期限を保存し、最終ボタンを「条件に同意して契約する」とする。確認チェックは未選択から開始する。失効・条件更新・本人確認未完了の場合は理由と必要操作を表示する。

ダミー規約はPreviewの確認用として維持できるが、実取引の同意や公開版の根拠にしない。画面文言だけで取引条件を確定させず、正式文書とサーバーの条件を一致させる。

## 返済と期限延長

返済画面では契約番号、指定日、元金、利息、費用、合計、振込先、振込名義、期限、更新時刻を表示する。予定日を変えるとサーバーで必要額を再計算する。複数契約の合算振込は初期範囲外とし、契約ごとの照合を基本とする。

振込先や名義はコピーできる。「振込済みを申告」は確認画面を経て実行し、完了表示を「入金確認中」にする。アプリ内送金・決済を実装していない間は「支払う」という即時決済を連想するボタンを置かない。

延長は、支払うべき利息、旧期限、新期限、延長条件を専用画面に分離して承諾する。現行の3か月延長を利用者が自由な期間に変えられるようにはしない。相談中・入金確認中・期限後などの可否はサーバーの状態に従う。

追加借入は相談受付であり、残高の即時増額ではない。再査定・変更条件・再承諾が必要なことを伝える。一つの契約の一部カードだけ返却する操作は初期範囲外とする。

## 発送と返却

申込後の発送画面に発送先、受付番号、梱包方法、必要な同梱情報、送料・保険・責任範囲を表示する。必要な運用が未確定なら発送ボタンを有効化しない。配送会社・追跡番号の登録と「発送連絡」を設け、配送システム連携がない間は自動追跡を装わない。

到着数不足・違うカード・ケース損傷等は追加情報依頼または査定内容の変更として表示する。運営側の検品は各明細の枚数・鑑定番号・状態・保管場所を管理し、利用者には必要な確認内容だけを提示する。

返却時は返送先を確認し、住所変更が必要な場合は本人確認と運営確認へ誘導する。追跡番号、発送日、対象カードを表示。返却済みの意味を「出荷完了」か「受取確認」かで曖昧にせず、管理画面の操作定義と合わせて確定する。

## 本人確認とアカウント

メール・パスワードによる既存Supabase Authを継続する。通常起動でログインを繰り返さず、保存したセッションを復元する。アプリAPIの通信障害をログアウトやパスワード不正として扱わない。ログインと本人確認の状態は別に表示する。

| 段階 | 画面仕様 |
| --- | --- |
| 未提出 | 必要な理由、運転免許証、登録情報の確認、所要時間は運営が確認した範囲だけ案内 |
| 撮影 | 表面と裏面を分けて撮影・選択。枠切れ・反射・期限等を確認するガイド |
| 送信前 | 2枚のプレビュー、氏名・住所との一致、利用目的・送信同意 |
| 確認中 | 提出日時、確認待ち。連打・重複提出を避ける |
| 再提出 | 不備理由と対象面だけを明示し、修正可能にする |
| 確認済み | 確認済みの表示。書類写真そのものをマイページに常時表示しない |
| 登録変更 | 本人特定情報の変更時は再確認が必要と事前表示。契約中の返却先変更と分ける |

書類画像は本人確認専用の非公開経路で扱い、カード画像検索AI・LINE・通知へ送らない。書類提出だけで本人確認が完了したと表示しない。免許証画像のみで採用する非対面本人確認方式が運用・法令上充足するかは、運営が公開前に確定する。

電話番号認証は契約の本人確認とは分ける。現在設定されていない機能を「認証済み」と表示しない。必須にするタイミングと提供サービスは既存の稼働設定を確認してから確定し、今回のUI案で認証方式の移行は決めない。

パスワード再設定はリンクから更新画面へ直接入り、成功後のログイン状態と次の操作を示す。期限切れリンク・別端末・失効した復旧セッションを区別する。メールアドレス変更は確認待ちを表示し、更新リクエスト成功を変更完了と混同しない。

## マイページ

既存の日本語設定メニューを基礎にする。アカウント領域は登録情報、本人確認、振込先、メール変更、パスワード変更。通知領域は通知設定。規約・サポート領域は利用規約、プライバシーポリシー、よくある質問、お問い合わせ。その他は退会・アカウント削除とログアウト。

融資・返済状況、査定履歴は取引状況の同じ画面へのリンクにする。別のコピー画面を増やさない。言語変更は置かない。通知拒否で申込できなくしない。退会の入口は削除対象・保持が必要な記録・契約中の扱いを説明し、現行のサポート相談だけの機能を即時削除機能と呼ばない。公開ストアのアカウント削除要件を満たす実フローは別途完成させる。

## お知らせとサポート

お知らせは取引連絡と運営告知を区別する。未読の件数は実際の未読だけを数える。同じ状態の再取得で新しい未読を増やさない。既読化の失敗で詳細を開く操作を遅らせない。

プッシュ通知には金額・カード名・本人確認書類などを含めず、「お手続きに更新があります」等を使用する。タップ後、ログイン・所有権確認を経て該当取引へ遷移。ログアウト中は宛先だけ保持し、ログイン後に権限を再確認する。案件が削除・統合済みなら一覧と案内を表示し、空画面にしない。

通知登録は端末トークンとアカウントの紐付けを一度ずつ処理し、トークン取得と更新通知を循環させない。通知を送れなくても契約更新の成功を失敗扱いにしない。お知らせ一覧を正規の確認先とする。

問い合わせは各取引から開ける共通画面にする。受付番号を表示しコピーできる。LINEを開く前に、相談案件の作成・紐付けを済ませる。初期はアプリ内チャットを追加せず、対応状況・運営からの依頼・利用者の回答を案件として記録する。LINEの会話を自動取得・自動送信する前提にしない。

## 失敗時と端末保存

| 状況 | 利用者に表示する内容 | 復帰方法 |
| --- | --- | --- |
| 起動直後・読込中 | 必要な範囲のスケルトン。金額を0として表示しない | 復元後に更新 |
| 通信不可・DNS・タイムアウト | 接続できなかったこと、保存済み内容の時刻 | 手動再試行。入力は保持 |
| ログイン失効 | ログインし直す案内 | 入力と戻り先を保持。別アカウントには渡さない |
| APIの権限不足 | 利用できない操作であること | ログインし直しを無限に要求せず、サポートへ |
| 外部検索の429 | 時間をおいて再検索、登録カード・個別相談 | 自動連打しない |
| 算出不可 | 個別査定が必要な理由 | そのまま相談申込へ |
| 操作の競合 | 他の更新があったことと最新状態 | 最新条件を取得し直し、承諾は取り直す |
| 送信結果不明 | 受付を確認中 | 同じ送信キーで照会。重複申込を作らない |
| 写真拒否・低容量 | 写真選択／手入力、軽量化・再撮影 | カード選択済み内容を保持 |
| 書類不備 | 不備の対象と修正方法 | 必要な面だけ再提出 |

下書きの保存項目は選択カード、枚数、申告状態、備考、最後に開いた工程、更新日時。本人確認書類、パスワード、銀行口座の入力途中は一般の下書き領域に保存しない。カード写真を保存する場合も本人確認写真と分離し、送信・破棄後に整理する。

ログアウト・アカウント切替ではその利用者の画面キャッシュ・機密情報を消去する。下書きはログアウト時に端末から削除する旨を事前に表示する。ゲスト下書きはログイン時に本人が引き継ぎを選ぶ。セッション切れによる一時的な再認証は、明示的なログアウトと分けて扱う。

起動・タブ切替だけで不要な検索・OCR・通知登録を繰り返さない。古いレスポンスは表示に反映しない。ページ単位の読込とキャンセル、同じ照会の重複抑制を採用する。

## 管理者画面との対応

管理者一覧は進行中の元本合計、対応が必要な件数、期限別の対象、査定待ち、出金待ち、返却待ちを示す。参考額・希望額・確定元本を混ぜて集計しない。

個別画面では同じ受付番号で、利用者、カード全明細、相談、書類確認状態、提示条件、検品、出金、返済、延長、返却、履歴を確認できる。書類閲覧と個人情報には担当権限を設け、内部メモと利用者への説明を分ける。

管理者の状態変更には必要項目と許可された次の状態を表示する。検品内容・鑑定番号・保管場所が不足する場合は、対象のカード行と不足項目へ直接移動する。抽象的なエラーだけを出さない。

LINE由来の手動作成は「連絡先だけの相談」と「アカウントに紐付いた取引」を区別する。メール・電話の一致だけで他人のアカウントに自動連携しない。本人確認済みの連携手続きと監査記録を必要とする。

状態変更はサーバーで確定した後に通知イベントを記録する。通知失敗は再送対象として扱い、融資状態の更新を巻き戻さない。同じ変更の二重通知を防ぎ、プッシュ停止端末でもアプリのお知らせには残す。

## データと権限の要件

- 読み取り用の取引一覧モデルで相談案件と融資契約を結合し、一つの表示IDと履歴を返す。業務台帳をUIのために書き換えない。
- 各金額に種別、算出日時、基準日、有効期限、条件版を持たせる。端末の時計だけで金融額を確定しない。
- カード明細と必要な個体情報、画像、鑑定番号を紐付ける。自己申告と検品済みを区別する。
- 配送状態、振込状態、本人確認状態、融資状態を別に持ち、複合状態の意味を崩さない。
- 利用者は自分の取引と許可された情報だけを閲覧。内部メモ・保管場所・他人の取引・書類は返さない。
- サービスの秘密鍵をアプリに入れない。書類のURLを公開しない。アプリAPIの認証をVercelの管理画面ログインと混同しない。
- 申込・承諾・取消・返済申告には重複防止、バージョン競合検出、操作者・日時・条件版の記録が必要。
- 解析イベントにカード画像・書類・認証情報・口座・自由記述を含めない。検索語も個人情報が混ざり得るため生の値を収集しない。

## 画像検索の初期実装（2026-11-03）

- 1枚の撮影画像につきOpenAI Responses APIを1回呼び、印字された名前・完全な型番・セット記号・言語・レアリティを抽出する。モデルの既定値は`gpt-4.1-mini`。画像比較による2回目のAI呼び出し、自動確定、価格・真贋・鑑定グレードの推定は行わない。
- 型番優先で自社DBと既存の外部検索アダプターを検索し、候補がない場合だけ名前で1回再検索する。各検索前に既存の外部検索レート制限を確認する。外部検索1回は検索HTTPリクエスト1件と商品詳細最大6件であり、全体を1通信とは数えない。外部検索ごとの共有時間予算は8秒。
- 分母を含む型番、明示されたセット記号・言語、ゲーム種別の矛盾を除外し、一致した情報を使って候補を最大3件に並べる。一致情報は確率ではなく照合根拠。商品メタデータに情報がない場合は断定しない。同型番の別イラストは利用者が確認する。
- 撮影画像と候補を表示し、利用者がカードを確定してから状態・枚数を選ぶ。撮影画像を変更したら以前の候補を消す。読み取り結果を表示し、修正して文字検索・再撮影・個別査定へ進める。
- 読み取り後に候補検索が失敗しても、抽出した文字を返す。同じリクエストIDの完了済み結果は再利用し、AIを再実行しない。画像送信同意、画像サイズ制限、日次上限、サーバー側のキー管理、トークン使用量の記録を維持する。
- `OPENAI_API_KEY`はVercel Previewのサーバー環境変数に保存する。キー未登録時の503は維持。外部データ利用の契約・画像の二次利用条件は別途確認する。

## 認識精度の改善と画像マスター計画（2026-11-03）

### 確認できた事実

- 買取チェッカーの[公式サイト](https://kaitori-checker.com/)と[プライバシーポリシー](https://kaitori-checker.com/privacy-policy)では、撮影・ライブラリ画像・スクリーンショットからの商品識別と、カード名・型番・レアリティ等の解析を説明している。公開資料から利用モデル、特徴量、距離計算、候補選別方式までは確認できない。以下は当アプリの設計案であり、競合の内部実装を確認したという意味ではない。
- 現行コードは画像を文字にして検索する方式であり、撮影画像と商品画像の類似検索ではなかった。
- `150/XY-P`のようなプロモ番号が旧パーサーの対象外で、照合根拠ゼロのカードも候補として残っていた。完全なプロモ番号・商品名の照合根拠を要求する修正を行う。
- 公開検索APIは`150/XY-P`では別番号のカードを返したが、`150 XY-P`で対象の商品ID `91395`を返した。外部リクエストの検索文字列のみ空白区切りにし、内部識別子は`150/XY-P`として厳密に照合する。
- PSAラベルの英語略称を印字カード名として採用しないよう指示を変更する。ただし、プロンプトの変更だけで画像認識全体の精度改善を保証しない。
- 対象Preview `mkmkkkdserlcaycknuxp`の読み取り調査では、`cards`は7行、画像URLの登録は0行、XY-Pカードの登録も0行。これはPreviewの状態であり、本家の本番マスターの網羅性を調査した結果ではない。

### 目標の照合処理

1. 写真からカード本体を検出して切り出す。PSAラベル・ケース枠・背景はカード本体と分ける。四隅を検出できる場合は傾きを補正し、不明瞭なら撮り直しへ案内する。固定位置で一律に切り抜いてカードを欠落させない。
2. 画像検索用モデルで本体画像の特徴量を算出し、参照画像の索引から上位候補を取得する。単に名前と画像URLをDBに入れるだけでは画像類似検索にはならない。
3. 印字名、完全な型番、セット、言語、レアリティで照合する。明確な番号・言語の矛盾を除外し、似た絵柄やパラレルは個別の印刷種として扱う。
4. 視覚的な一致が弱い場合や上位候補の差が小さい場合は、候補画像と撮影画像を比較して再順位付けするか、判別不能を返す。関係のない3枚で一覧を埋めない。画像距離をそのまま「正解確率90%」とは表示しない。
5. 利用者がカードを確定してから、確認済みの商品ID対応表を通して相場・参考額を取得する。認識マスターの有無と、最新の参考額を計算できるかは別の状態として扱う。

モデル候補は画像特徴抽出を提供する[DINOv2](https://github.com/facebookresearch/dinov2)と[SigLIP2](https://huggingface.co/docs/transformers/model_doc/siglip2)。カードの近似絵柄の識別精度・利用条件・実行時間を実画像で比較して選定する。競合がこれらを使用しているとは主張しない。特徴量索引には[Supabase pgvector](https://supabase.com/docs/guides/ai/vector-columns)を利用できるが、画像側と検索側のモデル・前処理の版を必ず揃える。重い画像モデルを毎回Vercel Functionsでダウンロードする構成は採らず、索引作成はバッチ、推論はモデルを保持できる実行先に分ける。

### マスターとアクセス範囲

| データ | 主な項目 | 用途 |
| --- | --- | --- |
| カード | 内部ID、正式日本語名、別名、完全な型番、セット、言語、絵柄・レアリティ、ゲーム | 価格や在庫の鮮度から独立した商品同定 |
| 参照画像 | カードID、画像参照先、画像ハッシュ、本体の切り出し、出所・利用条件 | 正面画像とケース写真を適切に扱う |
| 画像特徴量 | 参照画像ID、モデル・前処理の版、次元、ベクトル、索引版 | 画像類似候補の取得。異なるモデルの特徴量を混ぜない |
| 市場商品対応 | カードID、提供元商品ID、確認状態・日時 | 別版への誤接続を防ぐ |

初回材料は本家tcg-royalのカードマスターを候補にする。承認を受けて読み取る列は`public_uid,name,card_number,category,image_url`のみ。顧客・本人確認書類・認証情報・取引・価格は取り込まない。本番には書き込まない。Previewの別マスターへ取り込み、欠損・重複・画像利用条件を検証してから特徴量を作る。利用者が選んだ撮影画像を無断で学習用に蓄積しない。競合アプリのデータや画像をコピーして索引を作らない。

### 評価と導入

正解の商品IDを付けた実撮影画像で現行OCR方式と画像マスター方式を比較する。PSAケース、反射・斜め撮影、プロモ、同一名の別絵柄、同じ絵柄の別言語、マスター未登録カードを含める。参照画像そのものだけで評価せず、実写真と参照画像を分離する。Top-1／Top-3の正解率、誤ったカードの提示率、判別不能率、応答時間を測る。閾値は検証用データで調整し、別の評価用データで比較する。現時点では画像マスター・特徴量索引・本体検出器は未導入で、上記の精度を達成済みとは扱わない。


### 2026-11-03 申込リストと取得カード参照情報

### 2026-11-03 旧裏・識別語・画像比較検索

- 画像解析の出力にspecificTerms（最大4件。LV32、HP70、わざ名などの実際に見える語）とoldBack（true/false/null）を追加。No.026など図鑑番号を固有の型番として扱わない。旧裏は推定であり真正性判定ではない。黄枠だけでは断定せず、復刻や不鮮明な写真は不明とする。
- 検索順は型番、カード名＋優先識別語、カード名＋旧裏（ポケモンでoldBack=trueのみ）、カード名。重複語句を省き最大4検索。上位の強い候補が3件取れた場合はそこで止める。段階全体の開始予算20秒、各検索は既存の有界タイムアウトを継続。
- 3・4段階へ進んだ場合、候補を実際の画像で並べ替える。最大12画像、CDN許可リスト、リダイレクト禁止、各1.5MB/16MP以下、2並列、6秒取得予算、320×448以下に変換。撮影画像と商品画像をモデルで1回比較（12秒、store=false）。図柄・背景・枠・配置を比較し、机・スリーブ・鑑定ケースを無視する。
- 型番一致を先頭に維持し、残りを画像比較順に表示。類似率の捏造や自動確定は行わない。画像比較不能時は文字情報順位を維持する。候補不足時は水増ししない。
- 通常は読み取り1回、広い検索時は比較を加えて最大2回のOpenAIリクエスト。両方のトークン使用量を既存の検索記録へ合算。日次/分次上限は維持。サーバー最大75秒、端末の画像検索待機85秒。DB構造・本家カードDBは変更しない。

- 実画像検証で、該当旧裏が検索結果の10・11番目に存在し、従来6件取得では比較対象に入らないことを確認。画像検索だけ12候補まで取得・比較する（手動検索は6件を維持、キャッシュキーも分離）。LV32は検索先への送信時にLV.32へ正規化する。


### 旧裏のLV一致だけで検索を打ち切らない

- oldBack=trueの場合、LV/HP一致が3件以上でも第2段階で打ち切らず、旧裏検索と画像比較へ進む。レベルの一致を固有のカード識別とみなさない。
- 旧裏推定に反するDP-P等の明示的な近代セット番号を候補から除外。セット情報のないカードは推測で排除しない。旧裏と明示された候補を識別語のみの候補より優先して比較対象に残す。

- 追加の実画像検証でoldBack=nullでも同様の誤一致を確認。旧裏が不明のポケモンにも旧裏検索を仮説として行う（判定値は不明を維持）。LV/HP一致は旧裏判定の有無によらず一意ではないため、第2段階では終了せず次の検索と画像比較へ進む。
